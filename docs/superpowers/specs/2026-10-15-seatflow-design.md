# SeatFlow 演出选座系统设计

日期：2026-10-15

状态：用户已于 2026-10-15 审阅通过并要求制定实施计划；以下补充明确了边界和恢复验收，不增加业务范围。

## 1 目标和已确认事项

将现有飞机票项目改造成可开源的 Java 服务端演出选座项目，用于测试开发校招或实习展示。交付重点是业务闭环、明确的数据不变量、可重复运行的测试，以及可以复现的并发和故障实验。

用户已确认：

- 场景为剧院或演出选座。
- 支持指定座位、2 至 4 人连座、取消、超时释放、整单退款、模拟支付及自动化测试。
- MySQL 为场次座位归属的最终裁决者；Redis 用于座位图查询缓存。
- 用户拥有原项目源码的开源权利。
- 发布到当前连接 GitHub 账号 yibenwulong 下的新仓库。

项目工作名和默认仓库名为 `seatflow`。新代码根目录为工作区内的 `seatflow/`，作为独立项目和仓库准备，现有航空工程用于迁移参考。只向新仓库发布新项目目录，旧工程的令牌 CSV、环境地址、文档生成中间文件和 Git 历史不随之发布。

## 2 首版交付范围

首版交付 Java REST 后端、座位图接口、命令行演示脚本、测试与缺陷实验材料、容器运行配置、持续集成和开源文档。

业务包括：

1. 账号登录及 USER、ADMIN 角色；演示账号由开发环境种子数据创建。
2. 剧院、厅、演出与场次查询；管理员维护场次。
3. 场次座位图、票价区域和过道区块。
4. 指定 1 至 4 个座位购票；自动分配 2 至 4 个连座。
5. 一单对应一个场次，支持同场次多次购票。通过请求幂等防止重复下单，不再沿用用户只能购买同一航班一次的规则。
6. 15 分钟支付期限；主动取消、到期取消、支付成功和整单退款。
7. 默认模拟支付，可控制成功、失败、重复通知及迟到通知。
8. 通过适配器保留支付宝沙箱扩展，实际启用需要用户提供沙箱配置；默认启动与测试不需要个人支付或邮箱凭证。

首版采用整单退款，不引入跨场次购物车、部分退款、复杂营销定价或第三方素材依赖。固定演示数据可以只有一个剧院，但表结构与接口允许多个剧院和厅。

## 3 技术和代码组织

- Java 17、Spring Boot 3.5.13、Maven Wrapper。
- MySQL 8 系列、数据库迁移、显式事务及场次座位条件更新。
- Redis：短期座位图缓存，故障时查询回源数据库；不决定座位能否售出。
- RabbitMQ：订单事件和到期处理提示。数据库 Outbox 保存待投递事件，数据库到期扫描负责兜底。
- Java 自动化测试以 JUnit、Mockito、Spring Boot 测试支持为基础；真实数据库、Redis 和 MQ 集成测试采用容器环境。
- HTTP API 使用统一错误结构，参数校验、登录与角色检查在入口统一处理。
- 金额采用 BigDecimal，接口中的长整型 ID 输出为字符串。

按业务组织代码：`catalog`、`seating`、`booking`、`payment`、`identity`、`messaging`、`common`。使用清晰的服务和适配器边界，避免把所有流程集中在一个 Service 或消费者中。

航空特有实体、航段关联、机场映射、跨航段同座探测、固定 180 座偏好和旧蓝图逻辑不迁入新业务模型。

价格从服务端 SessionSeat 读取并形成订单快照，不接受前端金额作为计价依据。布局在场次开始销售后保持稳定；修改厅布局不改变既有场次的座位身份与订单快照。

时间统一由可注入 Clock 提供并按 UTC 保存，展示时显式转换时区。expireAt 为创建时间加 15 分钟与开演时间两者较早值，不晚于开演时间；不按消息入队时间重新计算。支付裁决使用锁定订单后读取的本地 Clock，now 必须严格早于 expireAt；恰好截止或之后均按迟到支付处理，即使订单尚未被扫描改为 CANCELLED。

## 5 座位与订单状态

场次座位状态：`AVAILABLE`、`HELD`、`SOLD`、`DISABLED`。

- AVAILABLE：可售，无当前订单所有者。
- HELD：由 ownerOrderId 暂时持有，保存 holdExpiresAt。
- SOLD：已支付，继续保存 ownerOrderId。
- DISABLED：布局或运营禁售，不参与分配。

订单状态：`UNPAID`、`PAID`、`CANCELLED`、`REFUNDING`、`REFUNDED`。

- 创建订单时在同一数据库事务中从 AVAILABLE 预占为 HELD。
- 支付确认将本人订单的 HELD 改为 SOLD，同时 UNPAID 改为 PAID。
- 取消或到期将本人订单的 HELD 改为 AVAILABLE，同时订单改为 CANCELLED。
- 退款申请将 PAID 改为 REFUNDING；网关确认退款成功后，在短事务中将本订单的 SOLD 释放为 AVAILABLE，并完成 REFUNDED。
- 迟到支付不重新占座，记录收款事实并创建持久化全额退款任务；仍为 UNPAID 的到期订单先经同一事务取消并释放原 HELD，已 CANCELLED 的订单不再次释放。原订单保持 CANCELLED，资金进度由支付和退款记录表达。
- NORMAL 退款完成时释放本订单 SOLD 座位并迁移 REFUNDED；LATE_PAYMENT 与 DUPLICATE_PAYMENT 退款只完成资金记录，不再次修改座位或原订单业务终态。

座位释放必须包含原 ownerOrderId 和预期状态条件。旧订单的取消或退款重放，不得改变已经由新订单持有的座位。

## 6 指定选座和连座

创建订单请求包含 `sessionId`、`requestId` 和一种分配模式：

- EXPLICIT：`seatIds` 为 1 至 4 个不重复座位，不允许同时传自动分配人数。
- ADJACENT：`count` 为 2、3 或 4，可选择票价区域，不能同时传 seatIds。

指定选座验证场次归属、售票状态、售票时间、座位是否禁售与是否全部 AVAILABLE。EXPLICIT 允许同场次内分散或跨排的座位；不跨排、不过道和连续性限制仅用于 ADJACENT。

连座必须同时满足同场次、同排、同 blockId、同票价区域和排内物理位置连续。过道、缺失座位、禁售座和已占座都会打断连续性；展示座号恰好连续不能证明连座。

自动分配按排和区块的稳定顺序选择合法候选组合。在事务中对候选组合执行条件预占，影响行数必须等于期望座位数。竞争失败时回滚整个事务，最多使用三个独立事务尝试不同候选；指定选座竞争失败直接返回冲突，不替换用户指定座位。

订单头、全部明细、全部座位预占和 Outbox 写入必须在同一事务完成。任何一座失败，都不能留下部分预占或有效订单。幂等键为 `(userId, requestId)`；相同键和相同请求返回原结果，相同键但不同载荷返回冲突。

不另设一个需要在支付时再次扣减的数据库数量库存。余票从场次座位状态聚合或缓存派生，物理容量和座位归属是最终依据。

## 7 并发控制与事务边界

座位预占使用带 AVAILABLE 条件的更新并核对完整影响行数，失败整体回滚；共享资源操作遵循稳定 ID 顺序，降低交叉抢座死锁风险。死锁与竞争重试有明确上限。

支付、主动取消和到期取消以数据库订单行作为串行裁决点，事务内读取当前状态并完成迁移。可以使用行锁或等价条件更新，但所有入口必须遵循相同锁定顺序：先订单，再按稳定顺序处理所属座位。

Redis 标记删除、消息 redelivered 属性和进程内锁不作为订单最终裁决依据。退款互斥和重复处理依靠数据库状态、稳定退款号与步骤记录，不依赖旧实现的固定值 Redis 退款锁。

外部支付请求不置于数据库长事务中。网关调用前后有可恢复的支付或退款记录，第三方成功但本地事务失败时能够再次查询和补尾。

## 8 支付与退款适配器

支付接口先检查订单归属、UNPAID 状态与未到期，使用服务端快照金额建立支付请求。

支付通知通过网关适配器验证来源和字段，核对订单、金额、商户身份、交易状态和交易号唯一性。重复通知不能重复出售或重复退款。每订单复用稳定商户支付请求号；若仍收到另一个真实交易号的第二笔收款，保存收款事实并创建 DUPLICATE_PAYMENT 退款，不能仅因订单已 PAID 就忽略资金事件。

MockPaymentGateway 使用可控的本地交易记录支持模拟支付、网关错误与重放。模拟完成入口仅在 local/test 配置启用，并校验访问身份；它不会作为真实支付能力对外宣传。

AlipaySandboxGateway 为可选适配器，通过环境变量启用；缺少配置时明确报告不可用，不使用个人回退配置。真实沙箱联调与 Mock 测试结果分别报告。

首版在开演前支持整单原路退款。使用退款申请时保存的金额快照全额退款；已开演订单拒绝普通退票。每笔退款使用稳定 refundId；退款记录区分网关成功、本地座位释放完成和最终完成，失败有有限重试及可查看原因。

## 9 缓存 消息和到期恢复

Redis 缓存场次座位图，包含生成时间，默认 TTL 为 5 秒。页面数据允许短暂陈旧，创建订单始终回数据库裁决；缓存不存在或 Redis 不可用时直接查数据库。

座位变更事务写入 Outbox，由后台投递缓存失效和订单事件。投递者以条件更新领取事件，领取租约默认 30 秒，进程退出后租约到期可以重领。发布成功要求 Broker confirm ACK 且没有不可路由 return；失败保留事件重试。发布后保存投递状态失败允许重复发布；数据库消费者的 eventId 去重记录与业务修改同事务提交，缓存失效等天然幂等操作可重复执行。最多自动尝试 10 次，退避间隔为 1、2、4 秒并封顶 60 秒，耗尽后保留 FAILED 和错误原因，避免无限立即重入队。

到期消息仅触发检查，数据库 expireAt 是准则。定时扫描每 5 秒处理已到期 UNPAID 订单，使用与主动取消相同的幂等释放服务。消息丢失或 MQ 暂时不可用，不能永久阻止到期回收。

Redis 缓存不保存唯一的预占事实，重建不会改变数据库座位归属。旧缓存重建的短暂陈旧最多影响展示，不允许绕过数据库预占。

## 10 主要接口

统一前缀 `/api/v1`，所有修改接口校验身份，管理接口校验 ADMIN。

| 方法和路径 | 功能 |
| --- | --- |
| POST /auth/login | 登录，返回令牌及必要用户信息 |
| GET /shows | 按城市、日期等条件查询演出 |
| GET /shows/{id}/sessions | 演出场次列表 |
| GET /sessions/{id}/seats | 布局与场次座位状态 |
| POST /orders | 指定选座或自动连座，并在一个事务内建单及预占 |
| GET /orders | 当前用户订单列表 |
| GET /orders/{id} | 本人订单及明细 |
| POST /orders/{id}/cancel | 取消本人未支付订单 |
| POST /orders/{id}/payments | 创建本人订单支付请求 |
| POST /payments/{provider}/notify | 验证网关通知并处理支付 |
| POST /orders/{id}/refunds | 申请本人已支付订单整单退款 |

## 11 测试设计和验收不变量

快速测试验证布局、连座算法、请求校验、金额和状态转换；真实集成测试验证 MySQL 事务、Redis 故障回源、Outbox/MQ 及 HTTP 权限。

关键不变量：

- 每个场次座位最多一个有效订单所有者；不同场次的同一物理座位可独立售卖。
- 有效容量等于 AVAILABLE、HELD 和 SOLD 座位之和，不把 DISABLED 算入可售容量。
- 指定选座和连座要么全部成功，要么无新增占用。
- 旧订单的释放不改变新订单所有者。
- 相同幂等请求不产生第二个订单，相同支付或退款事件不重复产生资金副作用。
- 已收款对应有效订单或可查询、可重试的退款任务；系统不得静默丢弃处理。
- 数据库订单、明细和座位状态按业务阶段一致，缓存可以陈旧但不影响裁决。

三个并发专项：

1. 32 个用户同时竞争同一座位，恰好一个有效预占；相同 requestId 重放仍是一单。
2. 重叠的 2、3、4 连座组合竞争，成功组合完整占用，失败组合零新增占用；ADJACENT 无法跨过道和跨排，EXPLICIT 分散选座允许。
3. 重复取消、旧释放消息、支付取消指定交错，验证所有权、幂等与资金补偿。

通过 CountDownLatch/Phaser、可注入 Clock 和测试桩控制时序，不使用任意 sleep 作为正确性证明。到期业务测试可推进 Clock；真实 MQ 延迟特性单独验证，不用假的快时钟冒充 Broker TTL 行为。

恢复验收还必须覆盖：退款网关成功后本地提交失败，重试复用 refundId 且只释放一次；Outbox 发布成功后保存状态失败，重复投递不重复产生副作用；MQ 不可用时到期扫描仍能释放。Fake 网关的成功事实独立于订单事务保留，避免测试把外部成功也一起回滚后造成假通过。

提交测试设计、执行入口、原始结果与缺陷复盘。只有实际运行的测试才报告通过；容器环境缺失时明确报告未运行，不能静默跳过后声称全部通过。性能数字只在固定环境实测后记录。
